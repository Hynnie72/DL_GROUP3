# Module `runner` — Experiment Execution and Analysis

**File:** `src/runner.py`  
**Dependencies:** `os`, `time`, `dataclasses`, `typing`, `matplotlib`, `numpy`, `pandas`, `torch`, `IPython.display`, `scikit-learn`, `psutil`, `platform`, `threading`, and other internal modules from `src/`.  
**Used by:** Main notebook, sweep notebooks, and `main.py`.

## Purpose

The `runner` module provides the central interface for executing, managing, evaluating, and comparing machine learning experiments.

It contains two main components:

- `ExperimentResult`: a dataclass that stores the configuration, training history, evaluation results, predictions, checkpoint paths, and other information produced by one experiment.
- `ExperimentRunner`: the main class responsible for running experiments, managing checkpoints, generating comparison tables and plots, performing detailed analysis, benchmarking inference, and printing automatic conclusions.

The runner integrates the following modules:

- `config`: defines experiment configurations.
- `data`: creates training and evaluation DataLoaders.
- `model`: constructs the MLP architecture.
- `trainer`: handles model training, checkpoint saving, and prediction.
- `evaluator`: computes evaluation metrics and generates evaluation visualizations.
- `experiments`: provides sweep definitions and comparison conditions.
- `utils`: provides device configuration, reproducibility, and experiment-name formatting.

## `ExperimentResult` (dataclass)

`ExperimentResult` stores all important information generated by one completed experiment.

| Field | Type | Description |
|---|---|---|
| `config` | `ExperimentConfig` | Configuration used to run the experiment. |
| `history` | `Dict[str, List[float]]` | Training and evaluation metrics recorded at every epoch. |
| `metrics` | `Dict[str, float]` | Evaluation metrics calculated using the BEST checkpoint. |
| `y_true` | `np.ndarray` | Ground-truth labels from the evaluation set. |
| `y_pred` | `np.ndarray` | Predicted class labels from the BEST checkpoint. |
| `y_prob` | `np.ndarray` | Predicted class probabilities from the BEST checkpoint. |
| `n_params` | `int` | Number of model parameters returned by `model.count_parameters()`. |
| `train_seconds` | `float` | Total time spent inside the training procedure. |
| `model_path` | `str` | Path to the BEST checkpoint. |
| `last_model_path` | `str` | Path to the LAST checkpoint. |
| `best_epoch` | `int` | Epoch at which the lowest evaluation loss was achieved. |
| `best_loss` | `float` | Lowest evaluation loss recorded during training. |

### Training history

The `history` dictionary contains four lists:

| Key | Description |
|---|---|
| `train_loss` | Training loss at each epoch. |
| `evaluation_loss` | Evaluation loss at each epoch. |
| `train_accuracy` | Training accuracy at each epoch (%). |
| `evaluation_accuracy` | Evaluation accuracy at each epoch (%). |

### BEST and LAST checkpoints

The runner maintains two checkpoint types:

| Checkpoint | Selection | Purpose |
|---|---|---|
| BEST | Lowest evaluation loss across all epochs. | Used for the main evaluation metrics, predictions, and detailed analysis. |
| LAST | Model state after the final training epoch. | Used to inspect or evaluate the final training state. |

The distinction is important: the BEST checkpoint is not necessarily the checkpoint with the highest evaluation accuracy.

The BEST checkpoint is selected using **minimum evaluation loss**, while evaluation accuracy is calculated separately.

## Checkpoint path management

### `_get_checkpoint_paths(experiment_name)`

Generates the checkpoint directory and file paths for one experiment.

The experiment name is converted into a filesystem-friendly name using `slugify()`.

Each experiment receives its own directory:

```text
artifacts/saved_models/
├── co_so_2_lop_an_256_128/
│   ├── best_checkpoint.pth
│   └── last_checkpoint.pth
│
├── dropout_0_5/
│   ├── best_checkpoint.pth
│   └── last_checkpoint.pth
│
└── co_batchnorm/
    ├── best_checkpoint.pth
    └── last_checkpoint.pth
```

The method returns a dictionary containing:

| Key | Description |
|---|---|
| `directory` | Experiment checkpoint directory. |
| `best` | Path to `best_checkpoint.pth`. |
| `last` | Path to `last_checkpoint.pth`. |

This structure keeps the checkpoints of different experiments separate.

## Running experiments

### `run(config, log_every=5)`

Executes one complete experiment and returns an `ExperimentResult`.

The method follows these steps:

1. **Reproducibility:** Calls `set_seed(config.seed)` to initialize the random states.
2. **Data loading:** Creates training and evaluation DataLoaders using the configured batch size and seed.
3. **Model initialization:** Constructs a fresh `MLP(config)` and moves it to `DEVICE`.
4. **Trainer initialization:** Creates a `Trainer` with the model, configuration, and device.
5. **Training:** Calls `trainer.fit()` to train the model and save BEST and LAST checkpoints.
6. **Checkpoint validation:** Checks whether both checkpoint files exist.
7. **BEST checkpoint loading:** Loads the BEST checkpoint and retrieves its epoch and evaluation loss.
8. **Evaluation:** Uses `trainer.predict()` on the evaluation loader to obtain predictions and probabilities from the BEST checkpoint.
9. **Result creation:** Computes metrics, counts model parameters, records training time, and creates an `ExperimentResult`.
10. **Result storage:** Stores the result in `self.results` using the experiment name as the key.

The method also prints a completion summary containing:

- Best epoch.
- Best evaluation loss.
- BEST checkpoint accuracy.
- LAST epoch evaluation accuracy.
- Training time.
- BEST and LAST checkpoint paths.

**Important:** `train_seconds` measures the **total elapsed time** of the entire experiment (from `time.perf_counter()` before `set_seed` to after the final prediction step). It includes data loading, model initialization, training, checkpoint loading and evaluation.

### `run_all(configs, log_every=5)`

Runs a list of experiment configurations sequentially.

```python
runner.run_all(configs, log_every=5)
```

For each configuration, the runner:

- Prints the current experiment number.
- Calls `run()` to execute the experiment.
- Stores its result in `self.results`.

This method does not return a DataFrame; it stores the completed results inside the runner.

## Experiment groups

### `groups()`

Returns the experiment group names in the order they first appear in `self.results`.

The method removes duplicate group names and only includes groups represented by experiments that have actually been run.

## Summary table

### `summary(sort_by=None)`

Generates a Pandas DataFrame containing one row per completed experiment.

The table distinguishes between metrics associated with the BEST checkpoint and metrics from the LAST training epoch.

### Summary columns

| Column | Description |
|---|---|
| `Experiment` | Experiment name. |
| `Group` | Experiment group. |
| `Architecture` | Network architecture. |
| `Parameters` | Number of model parameters. |
| `Best Epoch` | Epoch with the lowest evaluation loss. |
| `Best Evaluation Loss` | Lowest evaluation loss. |
| `Best Train Acc (%)` | Training accuracy recorded at the BEST epoch. |
| `Best Evaluation Acc (%)` | Evaluation accuracy calculated using the BEST checkpoint. |
| `Best Train-Evaluation Gap` | BEST epoch training accuracy minus BEST checkpoint evaluation accuracy. |
| `Macro Precision` | Macro-averaged precision from the BEST checkpoint. |
| `Macro Recall` | Macro-averaged recall from the BEST checkpoint. |
| `Macro F1-score` | Macro-averaged F1-score from the BEST checkpoint. |
| `Last Epoch` | Total number of recorded epochs. |
| `Last Train Acc (%)` | Training accuracy at the final epoch. |
| `Last Evaluation Acc (%)` | Evaluation accuracy at the final epoch. |
| `Last Evaluation Loss` | Evaluation loss at the final epoch. |
| `Last Train-Evaluation Gap` | Final training accuracy minus final evaluation accuracy. |
| `Training Time (s)` | Total experiment execution time in seconds (includes training, evaluation, checkpoint loading and prediction). |

### Understanding the Train-Evaluation Gap

The gap is calculated as:

\[
\text{Gap} = \text{Train Accuracy} - \text{Evaluation Accuracy}
\]

A positive and larger gap can indicate that the model fits the training data better than the evaluation data, which may suggest overfitting.

However, this difference should be interpreted together with the absolute accuracy values and other evaluation metrics.

The gap is expressed in **percentage points**, not as a percentage increase.

### Sorting

If `sort_by` is provided, the method checks whether the requested column exists and sorts the DataFrame in descending order.

```python
runner.summary(sort_by="Best Evaluation Acc (%)")
```

If the column does not exist, a `ValueError` is raised.

**Note:** Sorting is always descending in the current implementation, including when sorting by loss or gap columns.

### `best_name(key="Accuracy (%)")`

Returns the name of the experiment with the highest value for the specified metric.

By default, it selects the experiment with the highest `Accuracy (%)` in its BEST-checkpoint metrics.

```python
best_experiment = runner.best_name()
```

## Comparison plots

### `plot_group_curves(group, save=True, show=True)`

Plots the training and evaluation curves for experiments in a selected group.

The figure contains three panels:

| Panel | Metric |
|---|---|
| 1 | Evaluation Accuracy (%) |
| 2 | Evaluation Loss |
| 3 | Train Accuracy (%) |

The baseline is included as a reference line when available and is displayed using a black dashed line.

For sweep groups (8–10), the method uses `sweep_members()` to display the experiments belonging to the corresponding increasing sweep.

If no matching experiments have been run, the method prints a message and returns without generating a figure.

The figure is saved to `figures_dir/group_curves/<slug>.png` when `save=True`.

### `plot_final_comparison(save=True, show=True)`

Compares all completed experiments using two BEST-checkpoint indicators.

**Left panel — Best Checkpoint Evaluation Accuracy**

- Displays horizontal bars representing the BEST checkpoint evaluation accuracy.
- Sorts experiments by accuracy.
- Restricts the horizontal axis to a range around the observed values to make differences easier to see.

**Right panel — Best Checkpoint Train-Evaluation Gap**

- Displays the difference between training and evaluation accuracy at the BEST epoch.
- Red bars represent positive gaps.
- Green bars represent zero or negative gaps.

This plot helps compare model performance and potential generalization differences. Saved to `figures_dir/comparisons/final_comparison.png`.

### `plot_per_class_accuracy(save=True, show=True)`

Generates a heatmap showing the accuracy of every experiment on each Fashion-MNIST class.

- Rows represent experiments.
- Columns represent the 10 classes.
- Each cell contains the per-class accuracy (%).
- Predictions are taken from the BEST checkpoint.

The heatmap uses `Evaluator.per_class_accuracy()` to calculate the accuracy for each class.

It helps identify which classes are consistently difficult to classify and whether particular configurations improve performance on specific classes. Saved to `figures_dir/per_class/per_class_accuracy.png`.

### `available_sweeps() -> List[str]`

Returns the list of sweep parameter keys (`"num_layers"`, `"lr"`, `"batch_size"`) for which at least two experiments have been executed. Used internally by `print_conclusions()` and export helpers.

## Increasing parameter sweeps

The runner supports three increasing parameter sweeps defined in `src/experiments.py`.

The available parameters are:

| Parameter | Factor | Value | Axis scale |
|---|---|---|---|
| `num_layers` | Number of hidden layers | `len(hidden_sizes)` | Linear |
| `lr` | Learning rate (Adam) | `lr` | Logarithmic |
| `batch_size` | Training batch size | `batch_size` | Logarithmic |

The sweep logic uses `SWEEP_PARAMS`, `SWEEPS`, and `on_sweep()` from `src.experiments`.

### `sweep_members(param)`

Returns the names of experiments that differ from the baseline only in the selected parameter.

The comparison:

- Ignores `name` and `group`.
- Ignores the parameter being swept.
- Requires all other configuration fields to match the baseline.

The resulting experiments are sorted by increasing parameter value.

This means a sweep can include experiments from multiple groups, not just the dedicated sweep group.

For example, the learning-rate sweep can include:

- The baseline Adam configuration.
- Adam learning-rate experiments from group 5.
- Increasing learning-rate experiments from group 9.

The SGD experiment is excluded because its optimizer differs from the baseline.

### `sweep_table(param)`

Creates a DataFrame containing one row per experiment in the selected sweep.

The table includes:

- Swept parameter value.
- Experiment name and group.
- Best epoch and best evaluation loss.
- BEST epoch training accuracy.
- BEST checkpoint evaluation accuracy.
- Train-Evaluation gap.
- Macro F1-score.
- LAST epoch evaluation accuracy and loss.
- Number of parameters.
- Training time.

This table is useful for examining how a particular hyperparameter affects model performance and training cost.

### `plot_sweep(param, save=True, show=True)`

Generates a three-panel figure for an increasing parameter sweep.

**Panel 1 — Best Checkpoint Accuracy**

- Displays BEST checkpoint evaluation accuracy.
- Displays training accuracy at the BEST epoch.
- Annotates the evaluation accuracy at each parameter value.
- Marks the baseline value with a vertical dotted line.
- Uses a logarithmic x-axis when the selected sweep specifies `log=True`.

**Panel 2 — Generalization Gap**

Displays the BEST epoch Train-Evaluation Gap for each sweep value.

- Red bars represent positive gaps.
- Green bars represent zero or negative gaps.

**Panel 3 — Evaluation Accuracy Curves**

Displays evaluation accuracy across epochs for every experiment in the sweep.

The baseline curve is highlighted with a dashed line.

If fewer than two experiments are available, the method prints a message instead of generating the plot. Figure saved to `figures_dir/sweeps/sweep_<param>.png`.

### `print_sweep_conclusion(param, save_path=None)`

Prints a textual summary of one increasing sweep (delegates to `build_sweep_conclusion`). If `save_path` is given (`.md` or `.txt`), the same lines are also written to that file.

Prints a textual summary of one increasing sweep.

The output includes:

- Accuracy at each parameter value.
- The parameter value with the highest BEST checkpoint accuracy.
- The parameter value with the lowest BEST checkpoint accuracy.
- Their differences from the baseline in percentage points.
- The range of Train-Evaluation Gaps at the BEST epochs.
- The range of training times.
- The range of model parameter counts.

This method helps extract numerical observations for the experiment report.

## Detailed analysis

### `show_detail(name, save=True, show=True, save_report=False, report_dir=None, report_format="md")`

Displays a detailed evaluation report for one experiment.

The method uses the stored `ExperimentResult` and performs the following operations:

1. Prints the experiment name, architecture, and optimizer configuration.
2. Displays the BEST epoch, BEST evaluation loss, and BEST and LAST checkpoint paths.
3. Displays the stored evaluation metrics in a Pandas DataFrame.
4. Plots the training and evaluation learning curves.
5. Prints a classification report generated by scikit-learn.
6. Plots the confusion matrix.
7. Displays sample predictions and their predicted probabilities.
8. If `save_report=True`, writes a Markdown/text detailed report to `report_dir`.

All prediction-based analyses use the predictions stored from the BEST checkpoint.

Figures are saved under `figures_dir/detailed/<slug(name)>/`.

## Saving and reloading models### `load_model(name, checkpoint_type="best")`

Loads a previously saved checkpoint and reconstructs the corresponding MLP model.

Supported checkpoint types:

| `checkpoint_type` | Loaded model |
|---|---|
| `"best"` | BEST checkpoint, selected by lowest evaluation loss. |
| `"last"` | LAST checkpoint, saved at the final training epoch. |

The method:

1. Checks whether the experiment exists in `self.results`.
2. Selects the appropriate checkpoint path.
3. Checks whether the checkpoint file exists.
4. Reconstructs the model using `MLP(r.config)`.
5. Loads the model weights using `torch.load(..., weights_only=True)`.
6. Sets the model to evaluation mode using `model.eval()`.
7. Returns the reconstructed model.

An invalid checkpoint type raises a `ValueError`.

### `verify_saved_model(name, checkpoint_type="best")`

Verifies that a saved checkpoint can be reloaded and produces the expected evaluation accuracy.

The method:

1. Loads the requested BEST or LAST checkpoint.
2. Rebuilds the evaluation DataLoader.
3. Generates predictions using `Trainer.predict()`.
4. Calculates the reloaded accuracy.
5. Compares it with the expected accuracy.

The expected reference depends on the selected checkpoint:

| Checkpoint | Expected accuracy |
|---|---|
| BEST | `r.metrics["Accuracy (%)"]` |
| LAST | `r.history["evaluation_accuracy"][-1]` |

The comparison uses `np.isclose()` with an absolute tolerance of `1e-4`.

If the values match, the method prints:

```text
STATUS: VERIFIED SUCCESSFULLY
```

Otherwise, it prints a warning indicating an accuracy mismatch.

## Automatic conclusions

### `print_conclusions(save_path=None)`

Generates a textual summary from the experiments currently stored in `self.results` (delegates to `build_conclusions()`).

If `save_path` is given (`.md` or `.txt`), the conclusions are also written to that file.

The method first checks that at least one experiment has been completed and that the baseline exists.

It then prints:

1. **Baseline performance:** BEST checkpoint accuracy, BEST evaluation loss, and Macro F1-score.
2. **Group comparisons:** The highest- and lowest-accuracy experiments in each group, excluding the baseline.
3. **Best experiment:** The experiment with the highest BEST checkpoint accuracy.
4. **Lowest evaluation loss:** The experiment with the smallest BEST evaluation loss.
5. **Overfitting indicator:** The experiment with the largest BEST epoch Train-Evaluation Gap.
6. **Per-class analysis:** The hardest and easiest classes based on average per-class accuracy across all completed experiments.
7. **Sweep conclusions:** A summary of every sweep containing at least two available experiments.

### `build_conclusions() -> List[str]`

Returns the same lines as `print_conclusions()` but as a Python list (without printing or writing to disk).

### `build_sweep_conclusion(param) -> List[str]`

Returns the key numbers of one increasing sweep as a list of console-style lines. Called automatically by `print_conclusions()` and `build_conclusions()`.

## Inference benchmark

### `benchmark_inference(...)`

Measures the inference performance of selected experiments using their saved checkpoints.

```python
benchmark_inference(
    names=None,
    checkpoint_type="best",
    batch_size=256,
    n_warmup=10,
    n_runs=50,
    include_single_sample=True,
    plot=True,
    save=True,
    show=True,
    measure_memory=True
)
```

The method is decorated with `@torch.no_grad()`, so gradient computation is disabled during benchmarking.

### Parameters

| Parameter | Default | Description |
|---|---:|---|
| `names` | `None` | List of experiment names to benchmark. `None` selects all completed experiments. |
| `checkpoint_type` | `"best"` | Checkpoint to benchmark: `"best"` or `"last"`. |
| `batch_size` | `256` | Requested batch size for batch inference. |
| `n_warmup` | `10` | Number of warm-up forward passes excluded from timing results. |
| `n_runs` | `50` | Number of timed forward passes. |
| `include_single_sample` | `True` | Whether to benchmark single-image inference. |
| `plot` | `True` | Whether to generate comparison plots. |
| `save` | `True` | Whether to save the benchmark figure as PNG. |
| `show` | `True` | Whether to display the benchmark figure. |
| `measure_memory` | `True` | Measure model size (MiB) and peak CPU RAM. On CUDA, also measure GPU model memory and peak VRAM. |

### Benchmark procedure

The method follows these steps:

1. Checks that experiment results are available.
2. Validates the requested experiment names.
3. Determines whether CUDA is being used.
4. Creates an evaluation DataLoader and retrieves one sample batch.
5. Uses the same input batch for all selected experiments to ensure a consistent comparison.
6. Loads the requested checkpoint for each experiment.
7. Performs warm-up forward passes.
8. Measures repeated forward-pass execution times.
9. Computes batch latency, standard deviation, throughput, and optional single-image latency.
10. Stores the results in a DataFrame.
11. Sorts the DataFrame by throughput in descending order.
12. Optionally generates benchmark plots.

### GPU synchronization

CUDA operations are asynchronous. Therefore, the method calls:

```python
torch.cuda.synchronize()
```

before and after timed forward passes when CUDA is active.

This ensures that GPU operations have completed before the elapsed time is recorded.

The actual timing uses:

```python
time.perf_counter()
```

Warm-up passes are excluded from the reported timing measurements.

### Batch inference metrics

For a batch containing \(B\) images, let \(t\) be the average forward-pass time in seconds.

The benchmark calculates:

**Average batch latency**

\[
T_{\text{batch}} = \operatorname{mean}(t_1,\ldots,t_n)\times 1000
\]

Unit: milliseconds per batch.

**Batch latency standard deviation**

\[
\sigma_{\text{batch}} =
\operatorname{std}(t_1,\ldots,t_n)\times 1000
\]

Unit: milliseconds.

**Throughput**

\[
\text{Throughput} =
\frac{B}{\operatorname{mean}(t_1,\ldots,t_n)}
\]

Unit: images per second.

**Average processing time per image within a batch**

\[
T_{\text{per-image}} =
\frac{T_{\text{batch}}}{B}
\]

Unit: milliseconds per image.

This is the average batch-processing time divided by the batch size; it is not the same as measuring one image independently.

### Single-image inference metrics

When `include_single_sample=True`, the benchmark additionally measures inference with a batch containing exactly one image.

It reports:

| Metric | Description |
|---|---|
| `Độ trễ 1 ảnh - TB (ms)` | Mean single-image forward-pass latency. |
| `Độ trễ 1 ảnh - P95 (ms)` | 95th-percentile single-image latency. |

The P95 value represents a latency threshold below which approximately 95% of the measured runs fall.

Single-image latency is useful when evaluating the responsiveness of a model for one input at a time.

### Benchmark output columns

The returned DataFrame contains:

| Column | Description |
|---|---|
| `Experiment` | Experiment name. |
| `Group` | Experiment group. |
| `Architecture` | Network architecture. |
| `Parameters` | Number of model parameters. |
| `Batch B (ms)` | Average latency for a batch of B images. |
| `Batch B Std (ms)` | Standard deviation of batch latency. |
| `Throughput (images/s)` | Inference throughput. |
| `ms/image (batch)` | Average batch time divided by the batch size. |
| `Single-Image Latency Mean (ms)` | Mean single-image latency, when enabled. |
| `Single-Image Latency P95 (ms)` | P95 single-image latency, when enabled. |
| `Model Size (MB)` | Model parameter + buffer size in MiB (when `measure_memory=True`). |
| `CPU RAM Peak (MB)` | Peak process RSS increase in MiB (when `measure_memory=True`). |
| `GPU Model (MB)` | GPU memory allocated by the model in MiB (CUDA only). |
| `GPU Peak (MB)` | Peak GPU memory including forward-pass activations in MiB (CUDA only). |
| `Evaluation Acc (%)` | Stored BEST checkpoint evaluation accuracy. |

Here, `B` is the actual number of images in the retrieved batch. It may be smaller than the requested batch size if the available evaluation data does not contain enough samples.

**Important:** The `Evaluation Acc (%)` column always comes from the stored BEST checkpoint metrics, even when `checkpoint_type="last"` is selected for timing. Therefore, when benchmarking LAST checkpoints, this column is not the accuracy of the LAST checkpoint.

### Inference benchmark plots

### `_plot_inference_benchmark(df, batch_size)`

Generates three comparison panels:

1. **Throughput:** Images processed per second for each experiment.
2. **Latency:** Single-image average latency when available; otherwise, batch latency.
3. **Speed-accuracy trade-off:** A scatter plot comparing throughput against stored BEST checkpoint evaluation accuracy.

These plots help compare inference speed and predictive performance.

### `_load_model_quiet(name, checkpoint_type="best")`

An internal helper used by the inference benchmark.

It:

- Selects the BEST or LAST checkpoint path.
- Checks whether the file exists.
- Reconstructs the MLP model.
- Loads its saved weights.
- Sets the model to evaluation mode.
- Returns the model without printing the detailed messages produced by `load_model()`.

## Example

```python
from src import (
    FashionMNISTData,
    Evaluator,
    ExperimentRunner,
    CLASS_NAMES,
    BASELINE,
    select_experiments
)

# Initialize data and runner
data = FashionMNISTData("./data")

runner = ExperimentRunner(
    data=data,
    evaluator=Evaluator(
        CLASS_NAMES,
        data.evaluation_images
```

## Evaluation protocol and important considerations

- Every experiment is trained using a newly initialized MLP and newly created DataLoaders.
- The random seed is reset using `set_seed(config.seed)` before each experiment.
- The BEST checkpoint is selected according to the lowest evaluation loss, not the highest evaluation accuracy.
- The main metrics, stored predictions, confusion matrices, classification reports, and per-class accuracy analyses use the BEST checkpoint.
- LAST checkpoint metrics are represented separately in the summary table.
- The evaluation loader is used after every training epoch to monitor performance and select the BEST checkpoint.
- The current implementation uses the evaluation set for model selection; it does not provide a separate validation set.
- Each experiment is executed once with its configured seed. Small differences between experiments should therefore be interpreted with caution.
- Inference benchmarking uses the same input batch for the selected experiments, repeated warm-up passes, and repeated timed forward passes.
- Benchmark results depend on the execution device, hardware, batch size, and runtime conditions.
- The current inference benchmark measures forward-pass latency; it does not measure checkpoint loading time, data preprocessing time, GPU memory consumption, or the full end-to-end inference pipeline.
